# 第 23 章 · 从这里继续

**本章目标**：知道怎么加新功能、怎么验证没改坏、怎么发布给别人玩、下一步学什么。

**开始之前**：前 22 章。你应该已经有一个"能打、有规则、有对手、手机上也能玩"的游戏，外加一个独立的跳球小玩法。

## 1. 先做一次自查

对照下表逐项过一遍，有一项不过就回去修：

- [ ] 双击 `index.html` 就能玩，不需要服务器
- [ ] 开球能把球堆打散，母球不会卡在球堆里
- [ ] 拖拽方向与球杆方向相反，力度条跟手
- [ ] 手中球能摆位，摆到不合法的位置会退回
- [ ] 球撞库会反弹，撞两次后明显变慢
- [ ] 球进袋消失，母球进袋判犯规并给对手手中球
- [ ] 分球组正确：第一次进球后锁定球组
- [ ] 打完自己组的球，状态提示"打黑八"
- [ ] 美式黑八必须先指定袋，进错袋判输
- [ ] 一局结束有弹窗，显示用时
- [ ] 刷新页面，战绩和设置还在
- [ ] 手机横屏能全屏打，面板能当抽屉用
- [ ] 跳球挑战能从页头 / 面板打开，三关都能过，「瞄准圈」开关关掉也还能打
- [ ] 控制台没有红色报错

## 2. 怎么加功能（三个真实例子）

### 例 1：加一颗"练习用"的目标球

改动只在一处：

```js
// js/balls.js 的摆球函数里，多加一颗
balls.push({ id: 3, x: 700, y: 310, vx: 0, vy: 0, active: true });
```

不用改渲染、不用改物理、不用改碰撞——**因为球是数据**。这就是第 3 章"球是数据，画是另一回事"的回报。

### 例 2：加一条新规则（"三次犯规判负"）

1. `state` 里加一个字段：`foulCount: [0, 0]`
2. `endShot()` 判犯规的地方 `state.foulCount[me] += 1`
3. 达到 3 次时调 `endGame(1 - me, '对手三次犯规')`
4. `updateStatus()` 里显示"犯规 2/3"

**规则的加法永远是这三步：加状态 → 在结算处判定 → 在界面显示。**

### 例 3：加一个新难度"大师"

```js
// js/ai.js
const LEVELS = {
  easy:   { angleErr: 2.2, powerErr: 0.10, planRate: 0.85 },
  normal: { angleErr: 1.0, powerErr: 0.05, planRate: 0.95 },
  hard:   { angleErr: 0.6, powerErr: 0.03, planRate: 1.00 },
  master: { angleErr: 0.3, powerErr: 0.02, planRate: 1.00 }   // 新增
};
```

再在 HTML 的模式行加一个按钮。**难度的本质是误差大小，不是算法复杂度**（第 16 章）。

### 例 4：加一个独立小玩法（跳球挑战）

我们真的加过一个：一个和主对战**完全不共享状态**的小玩法。做法不是"在主状态机里加个模式"，而是：

1. 新建 `js/jump.js`，用 IIFE 包起来，只往 `window` 上暴露 `open / close / step / state`
2. 在 `index.html` 里加一个浮层、一个入口按钮、一个样式文件
3. 主玩法的 `state`、主循环、规则**一行都不动**

完整过程（含假想球几何、难度分档、自动验证）在第 22 章。这里只说结论：**新功能如果能独立，就别塞进老功能里。** 独立的东西坏了，删掉就行；混在一起的东西坏了，你不敢删。

## 3. 怎么验证"没改坏"

我们实际用的三种手段，你也可以照做。

### ① 物理回归脚本（不需要浏览器）

把物理函数抽出来，用 `node` 跑断言：

```js
// test_sim.js
const assert = require('assert');
// 造两颗球，正撞，断言"动的球停下、静止球获得速度"
assert.ok(Math.abs(a.vx) < 1e-6, '母球应停下');
console.log('全部断言通过');
```

```bash
node test_sim.js
```

能离线跑、几毫秒出结果，**改物理参数后必跑**。

### ② 无头浏览器截图

```bash
chrome --headless=new --screenshot=out.png --window-size=1440,900 file:///D:/my-pool/index.html
```

用来检查"布局有没有被挤坏"。第 18 章发现计时错位、第 20 章发现球号被裁，都是这么看出来的。

### ③ 手动清单

改完 UI 就把自查表里相关几项手点一遍。**5 分钟的检查，省 30 分钟的返工。**

## 4. 发布给别人玩

三种方式，从简到繁：

| 方式 | 做法 | 适合 |
| --- | --- | --- |
| 直接发文件夹 | 打包 zip 发给朋友，解压后双击 `index.html` | 最快，适合测试 |
| GitHub Pages | 推到仓库，Settings → Pages 选 main 分支 | 有链接、能分享、自动更新 |
| 对象存储 / 静态托管 | 上传到 OSS、Vercel、Netlify | 想要自定义域名 |

**注意**：用 `file://` 打开时，`localStorage` 是按文件路径隔离的；换成 `https://` 后，之前的战绩不会带过去（不同的 origin）。这属于正常现象。

## 5. 性能：现在还很宽裕，但知道上限在哪

一帧的开销大致是：

| 项目 | 量级 |
| --- | --- |
| 物理（16 球、240 步/秒） | 每帧 4 步 × 120 对碰撞 ≈ 0.1ms |
| 绘制（台面 + 16 球 + 光晕） | 0.5–1.5ms |
| DOM 更新（状态 / 力度 / 计时） | 0.1ms（且有"变了才写"的保护） |

60fps 的预算是 16.7ms，现在用了不到 2ms，**余量很大**。

真要扩展时注意三点：

1. **别在每帧里创建对象**（`new` 很贵），复用即可
2. **别在每帧里改 DOM 文本**（第 18 章的 `if (txt === last)` 就是这个）
3. **光晕/渐变的 `createRadialGradient` 可以缓存**，别每帧重算

## 6. 下一步可以学什么

按"从这门课能自然接上"的顺序：

1. **模块化**：把全局变量改成 `import / export`（代价是要起一个本地服务器）
2. **TypeScript**：给 `state`、`ball` 加类型，改字段时编译器会提醒你哪里漏了
3. **构建工具（Vite）**：热更新、打包、压缩
4. **游戏引擎**：Phaser、PixiJS（2D）、Three.js（3D）——你会发现物理和渲染的分离思想是通用的
5. **状态机库**：XState —— 第 14 章那套 `phase` 就是最简单的状态机

**但别急着上框架。** 你现在这套三千八百多行的原生实现，已经把"输入 → 状态 → 物理 → 规则 → 渲染 → 界面"整条链路走通了一遍。这个理解比会用一个框架值钱得多。

## 7. 最后：三条会一直有用的经验

1. **先能让它跑，再让它好看，最后让它快。** 顺序反了就会卡在"优化一个还不存在的功能"上。
2. **每个参数都要有一个"为什么是这个值"的故事。** 说不出来，说明你还没调够。
3. **用户说"感觉不对"，往往是对的。** 我们这个项目里，几乎每一次手感变好，都是因为用户描述了一个具体场景（"拖动母球时线乱跑""提示看不完""打开面板就不居中了"），而不是因为某个理论。

祝你的下一款游戏也顺利。
